## 二、旧脚本的问题定位

登录是四步，旧脚本在第 3、4 步各有一处缺陷，而且互相掩盖，所以表面上只表现为「提示登录成功，但列表里没有账号」。

```
① 申请二维码  →  ② 轮询扫码状态  →  ③ 取登录凭据  →  ④ 校验凭据 / 写入账号
   generate()       poll()            ← 缺陷在这        ← 缺陷在这
```

### 问题 1：凭据的读取位置变了（最关键）

**旧代码**（`poll()` 中，`scan_code == 0` 之后）：

```python
cookies_info = self._extract_cookies_from_url(url)
```

它假设登录字段是拼在 `data.url` 的查询参数里返回的，即旧格式：

```
https://passport.biligame.com/crossDomain?DedeUserID=<uid>&SESSDATA=<...>&bili_jct=<...>
```

而实际拿到的是新格式，`data.url` 里只有一个 ticket 参数：

```
https://passport.biligame.com/crossDomain?ticket=<TICKET>
```

登录字段实际在**响应头 `Set-Cookie`** 中返回。旧代码从未读取响应头，因此 `_extract_cookies_from_url()` 恒返回空字典，后续自然拼不出可用的 Cookie。

**对应日志**（`cookies` 里只有 url 和各 buvid 字段，没有任何登录字段）：

```
登录成功
登录成功但未取到用户ID，cookies: {'scan_code': 0, 'url': '...ticket=<TICKET>',
  'refresh_token': '...', 'timestamp': <ts>, 'buvid3': '...', 'buvid4': '...', 'b_nut': '...'}
```

### 问题 2：`KeyError: 'data'` —— 旧的 UA 标识不再被接口接受

旧脚本所有请求统一使用这个 UA：

```
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.3
```

`Chrome/58` 是 2017 年的版本号。使用它请求时，接口会直接返回 **HTTP 412**，首页响应也不再下发 `buvid3` / `b_nut`。于是这一行就炸了：

```python
buvid3_and_bnut = get_i_c().fetch_buvid3_and_bnut()
cookies["b_nut"] = buvid3_and_bnut['data']['b_nut']   # ← KeyError: 'data'
```

`fetch_buvid3_and_bnut()` 在取不到值时，返回的字典里**不含 `data` 键**，这一行直接抛异常，整个轮询回调被外层 `except` 吞掉，登录流程就此中断。

同一原因还会产生一条误导性日志：`[SSL] 测试请求返回错误状态: 412` —— SSL 检测那次请求没带 UA，被接口拒绝，脚本误判为「SSL 验证不可用」。

### 问题 3：账号保存失败却没有任何提示

```python
uid = int(cookies.get('DedeUserID', 0))
if uid <= 0:
    log_save(obs.LOG_ERROR, "无法获取用户ID")
    return                       # ← 直接 return
```

两处缺陷：

1. **`return` 之前没有停掉定时器**。`check_poll` 由 `obs.timer_add(check_poll, 1000)` 驱动，每秒执行一次。这里的 `return` 跳过了后面的 `should_stop = True`，定时器会继续拿**已经消费过一次的 `qrcode_key`** 去轮询。服务端对该 key 的应答是 `86038`，即「二维码已失效」。这就是「先看到登录成功，一秒后又看到二维码已失效」的来源——**后一条是脚本自己造成的**。

2. **`add_user()` 的返回值被丢弃**：

```python
get_b_u_c_m().add_user(cookies)   # 可能返回 {"success": False, "message": "缺少必要字段: b_nut"}，但没人检查
```

`add_user` 内部要校验 6 个必需字段（`DedeUserID`、`DedeUserID__ckMd5`、`SESSDATA`、`bili_jct`、`buvid3`、`b_nut`），缺任一个就静默失败。日志上看不出异常，只会觉得「点了登录，为什么列表还是空的」。

### 问题 4：`SESSDATA` 被二次 URL 编码，校验接口恒返回 -101

这条最隐蔽。`Set-Cookie` 下发的 `SESSDATA` **本身已是 URL 编码形式**，值里带 `%2C`：

```
SESSDATA=<hex>%2B<...>%2C<...>%2C<timestamp>
```

旧脚本拼接 Cookie 头的函数又无条件 `quote()` 一次：

```python
value_str = quote(value_str)        # %2C → %252C
```

发出去就成了 `SESSDATA=...%252B...%252C...`，服务端按 URL 解码后得不到原值，用户信息校验接口返回：

```json
{"code": -101, "message": "账号未登录"}
```

**注意：这个响应里没有 `data` 字段**。而 `get_uid_nickname_dict()` 是这样用的：

```python
is_login = nav_info["success"]
if is_login:
    uid_nickname_dict[get_b_a_g().get_bilibili_user_card(uid)['data']['data']['card']['name']] = uid
else:
    get_b_u_c_m().delete_user(int(uid))     # ← 账号被移除
```

于是表现为：账号刚存进去，一点「更新账号列表」就消失，下拉框为空。

### 问题 5：请求一失败就移除账号

接着上面那段 `else`。旧逻辑把**「校验请求失败」一律等同「账号已失效」**，包括：

- 请求超时
- TLS 握手失败
- HTTP 412（请求被拒）
- 服务端 5xx

全部走 `delete_user()`。只要网络不稳，账号就会被自动清掉。

而 `-101`（凭据确实失效）与其它错误，在旧代码里无法区分。

### 问题 6：昵称接口一异常，整个账号列表就空掉

```python
get_b_a_g().get_bilibili_user_card(uid)['data']['data']['card']['name']
```

三层硬下标，任一层缺失就 `KeyError: 'data'`。名片类接口受限流、账号隐私设置等影响会返回非预期结构。

另外 `get_default_user_nickname()` 用 `list(...).values().index(...)` 反查昵称，默认账号只要不在字典里就抛 `ValueError`，登录状态直接无法显示。

## 五、常见问题

**Q：为什么不动原脚本，而是新增一个文件？**

该脚本是 140 万字节、3 万多行的单体文件。直接改原文件有两个问题：一是无法做新旧对比，出问题难以判断归因；二是后续与上游同步时必然冲突。新增文件可保持原脚本为上游状态，回退只需换回勾选。

**Q：只改 `general_script/bili_live_login_start.py` 这些源码模块可以吗？**

`finishedProduct/` 下是打包好的单体脚本，OBS 实际加载的就是它，与 `function/`、`general_script/` 中的模块**没有运行时关系**。改源码模块只对「从源码重新打包」有意义。本次修复落在成品脚本上；源码模块中的同名问题依然存在，后续做源码重构时需同步处理（改动点见第三节）。

**Q：`bilibili_live_multi.py` / `obs26.py` / `monolithic.py` 是否也有同样问题？**

有。这几个成品脚本共用同一套登录实现，同样是旧 UA + 从 `data.url` 取字段 + 二次编码。本次修复仅针对 `py36_obs27` 这条线（OBS 28+ / OBS 30+ 使用该版本）。

**Q：已有账号数据会不会丢？**

不会。配置文件路径未变，新脚本直接读取原有数据；登录成功后会刷新对应记录。

**Q：日志里仍然出现 412？**

说明当前运行的**不是**新脚本（新脚本已为该请求补 UA）。请检查是否同时勾选了新旧两个脚本，或 OBS 未重新载入脚本。

**Q：要换绑账号怎么做？**

登录新账号 → 自动进入列表 → 在「用户」下拉框选中它并设为默认。其它账号会在下次「更新账号列表」时校验，仅当服务端明确返回 `-101` 时才会被移除。

> 完整的界面操作步骤（首次扫码、切换、登出、删除、数据备份位置）见：[loginfix使用说明.md](loginfix使用说明.md)。
